# Dependent fields

Status: in progress (2026-10-22). Implemented and verified, awaiting review; website docs and the consumer skill reference remain. Branch: `dependent-fields`.

## Goal

Let a form field's items depend on other fields' values, such as a city lookup that lists the cities of the selected country. It works for every items-based editor (selects and the other choice editors, lookups, multi-lookups), on create and edit pages, in create sheets, and in inline grid rows.

## Decisions (Jerrie, 2026-10-22)

1. Make the field builder generic (`ResourceFieldBuilder<TResource>`) as a separate first step, before the dependency work. Typed `DependsOn(a => a.CountryId)` needs it, and so do later typed field features.
2. Checking that a child value matches its parent on save is left to the app's validation; nothing is built in.
3. While a parent is empty, its dependent fields are disabled.
4. Inline grid editing is in scope, not a follow-up.
5. A UI prototype covering several editors comes before any coding changes.

## Approach

When a parent field changes, the client posts the parents' current values to a field refresh endpoint. The server binds them to a new model and renders the field's dependents, including dependents of dependents, in one response with their usual editor templates (form or grid), and htmx swaps them in. No editor carries its own cascade logic. Lookup sheets also send the parent values with their sheet and search requests, which are GETs, so only the parents travel and the URL stays short.

Item loaders receive what the field's parents give them, and run only once every parent has a value (until then the field is disabled). A field always declares its parents with `DependsOn`; they aren't inferred from a filter. The model a loader receives has only the declared parents filled in (plus the record's key on an edit, from the route); any other field holds its default, so a filter must declare every field it reads.

A refreshing field is overlaid, not disabled, so a save started mid-refresh still posts its value. Inline rows identify the page and row the same way lookups pass `Form` today, since each row has its own field prefix and several can be open at once.

## API (agreed 2026-10-22, revised the same day)

```csharp
fields.Add(trip => trip.CityId)
    .DependsOn(trip => trip.CountryId)
    .UseEditor<SelectEditor>(select =>
        select.UseItems<VoyagerDb, City, int>(c => c.Id, c => c.Name, items =>
            items.Where((City city, Trip trip) => city.CountryId == trip.CountryId)));

// Optional empty text; generated by default ("Select Country first")
fields.Add(trip => trip.NeighbourhoodIds)
    .DependsOn(trip => trip.CityId, city => city.EmptyText = "Choose a city to see its neighbourhoods")
    .UseEditor<ToggleGroupEditor>(...);

// Choice editors load from a delegate that gets the typed form
select.UseItems((Trip trip, IServiceProvider services, CancellationToken ct) =>
    services.GetRequiredService<CityCatalog>().ChoicesForCountryAsync(trip.CountryId!.Value, ct));

// Registered lookup sources are value-based, so one source serves every form: it declares the value it needs,
// and each field maps its form to that value
public sealed class CitySource(CityCatalog catalog) : ILookupSource<City, int, int>
{
    public Task<IReadOnlyCollection<City>> FindAsync(IReadOnlyCollection<int> values, CancellationToken ct) => ...;
    public Task<LookupPage<City>> SearchAsync(int countryId, LookupQuery query, CancellationToken ct) => ...;
}
// The form's type is a fifth type argument: C# can't infer it once the others are named (see Implementation)
lookup.UseItems<CitySource, City, int, int, Trip>(c => c.Id, c => c.Name, trip => trip.CountryId!.Value);
```

- `DependsOn` may be called more than once for several parents, and parents chain (country → city → neighbourhoods). Inline rows use the same fields, so they cascade too.
- Loaders see only the declared parents (and the key on an edit); a filter reading `trip.Region` needs `.DependsOn(trip => trip.Region)`.
- `EmptyText` is the disabled field's empty text and a choice group's message box, set per parent. The lookup sheet's subtitle is always generated, listing every parent ("Filtered by Country: Japan, Star rating: 4").
- A source needing several values declares a small record (`CityFilter(int CountryId, string? Region)`) that the field builds from its form.
- `FindAsync` (loading the selected items by value) takes no argument: it doesn't depend on the parents.
- Existing interfaces and overloads are unchanged. Integrations (`LookupItems`, such as EF Core's) get the bound form as an untyped `LookupQuery.Model`.

New public surface:

- StellarAdmin: `ResourceFieldBuilder<TResource>` (step 1); `DependsOn(field)` and `DependsOn(field, configure)`; `FieldDependencyBuilder` (`EmptyText`); `ChoiceEditor.UseItems<TModel>(loader)`; `ILookupSource<TEntity, TValue, TArgument>` with `UseItems<TSource, TEntity, TValue, TArgument, TModel>(value, title, argument)` (and a `configure` overload) on the lookup and multi-lookup editors; `LookupQuery.Model`.
- StellarAdmin.EntityFrameworkCore: `Where<TModel>((entity, form) => ...)` on `EfCoreChoiceItemsBuilder` and `EfCoreLookupItemsBuilder`.

## Implementation

Built 2026-10-22, uncommitted until reviewed:

- `DependsOn` stores the parents on the field; `DependencyCheck` resolves them on the same form and reports a parent that isn't an editable field of it (`UnknownParentField`) or that closes a cycle (`DependencyCycle`), dropping that dependency.
- A field is disabled while a parent is empty: null, blank text, an empty collection, or the default of a number, date or ID (a new record's `0`); a Boolean or an enum always counts as set. Its items aren't loaded meanwhile. The hint is the first empty parent's `EmptyText`, or "Select {label} first".
- A disabled field posts an empty value (a hidden input, or the collection marker), so a save after the parent changed clears it rather than keeping the old value.
- Dependents render in `admin-dependent-field`, which names the field, its parents' input names, field names and labels, and its refresh URL (`Dependents`, a POST with the form, key, field prefix, sheet level and grid layout). The script posts every parent value in the form or grid row as `Model.Field`; the server binds only the parents of the affected fields to a fresh model and renders them, and each element is replaced.
- Lookup sheet and search URLs carry the same `Model.Field` values; an edit form's lookup URLs now include the record's key. A search whose parents are empty returns 404.
- `ChoiceEditor.UseItems<TModel>`: the loader gets the form's model; a form of another type is a configuration problem for the field. The EF Core choice loader now uses it, to apply `Where`.
- Generated texts ("Select Country first", "Filtered by Country: Japan") are English, in the templates and the script, not in `ResourceLabelOptions`.

Deviation from the agreed API: `lookup.UseItems<CitySource, City, int, int>(..., (Trip trip) => ...)` doesn't compile, because C# infers no type argument once any is named, so the form's type is a fifth type argument, `UseItems<CitySource, City, int, int, Trip>`. Needs Jerrie's OK.

## Open

- Come back to before the plan closes (Jerrie, 2026-10-22): drop the fifth type argument of the value-based lookup `UseItems` if possible. The field builder knows the form's type (`ResourceFieldBuilder<TResource>`), but `UseEditor<TEditor>(Action<TEditor>)` passes only the non-generic editor, so the lookup's `UseItems` can't infer it. Fixing it means carrying the type into the editor's configuration, which is new public API.

- Field change callbacks (`OnChange`) that update other fields' values on the server could reuse the same refresh endpoint. Whether to design for it now is undecided.

## Prototype

`sandbox/html/dependent-fields.html` (2026-10-22), built from editor markup captured from AdminPlayground's field editor gallery and the destinations inline row. A Trip create form (country select → city select, overnight stop lookup, arrival airport card lookup, guides multi-lookup; city → neighbourhoods toggle group, pickup points checkbox group) and two inline edit rows cascade live against a simulated refresh, and a matrix shows each editor in each state. Open visual questions, switchable on the page: the disabled hint, choice groups without a parent, the refreshing indicator, feedback when a value is cleared, and whether the lookup sheet names its filter.

Jerrie's picks so far (2026-10-22): the hint is the field's empty text; a choice group without a parent shows a message box; a cleared value is cleared silently, as in Filament, Nova and Salesforce (highlight styles and a note were tried and dropped); the lookup sheet names its filter. Messages are generated from the parent's label and selected title only ("Select Country first", "Filtered by Country: Japan"), with no articles or lowercasing, and the app can supply its own wording on `DependsOn`; the page switches between the two. While refreshing, a skeleton overlays the existing control (a `::after` on the control's wrapper, no markup swap), so it has the control's exact size; multi-line controls and groups take the box radius.

The existing disabled styles of the native select, buttons, input groups, toggles and checkboxes cover every disabled editor, which supports keeping StellarAdmin.UI unchanged. Lookup wrappers are `display: contents`, so state styles must target their children.
