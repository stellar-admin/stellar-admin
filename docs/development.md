# Development and verification

## Checkout and setup

This product repository is self-contained for builds, tests, and consumer reference generation. The website remains an independent repository and is needed only for website integration/export tasks. Run commands here unless another working directory is stated; inspect status separately in every repository you change.

Use the .NET SDK declared by the relevant `global.json`, restore the repo's local .NET tools, and use the checked-in package manager/lockfile for each client project. The product SDK is currently pinned to 10.0.400. Website uses pnpm; library clients use npm. Read `package.json` for available scripts. Do not silently change SDK pins or dependency versions to fit a machine.

## .NET project and dependency changes

Use the .NET CLI to create projects (`dotnet new`), add or remove solution projects (`dotnet sln ... add/remove`), manage project references (`dotnet reference add/remove --project ...`), and add, update, or remove NuGet packages (`dotnet package add/remove --project ...`). Never edit `.csproj` or `.slnx` files directly when a CLI command supports the change. Keep package versions centrally managed in `Directory.Packages.props`; package commands should update central versions as well as project references. Direct MSBuild edits are reserved for settings without a corresponding CLI command.

For TUnit, follow the [official console-project setup](https://tunit.dev/docs/getting-started/installation/): create a console project with the pinned framework, add `TUnit` through the CLI, and remove the generated `Program.cs` so TUnit supplies the entry point. Add a direct reference to the SUT project and add the test project to `StellarAdmin.slnx` through the CLI.

`global.json` selects Microsoft.Testing.Platform for the .NET 10 `dotnet test` runner, following the [official runner configuration](https://learn.microsoft.com/en-us/dotnet/core/testing/unit-testing-with-dotnet-test#mtp-mode-of-dotnet-test). TUnit supplies the test-project metadata used for solution discovery. New TUnit projects added to `StellarAdmin.slnx` are automatically included by both workflows. `--minimum-expected-tests 1` rejects a discovered test application that runs no tests; do not suppress that exit code. Unit and integration test projects use the same runner and discovery command; no legacy test executables or individual test-project workflow steps remain.

## Public API changes

The three packaged projects use PublicApiAnalyzers. Each lists its public API in `PublicAPI.Shipped.txt` (what a released package contains) and `PublicAPI.Unshipped.txt` (changes since then). Adding, removing or changing a public member fails the build with RS0016 or RS0017 until the list is updated. Update it from the repository root, with the project whose API changed:

```bash
AllowMissingPrunePackageData=true dotnet format analyzers src/StellarAdmin/StellarAdmin.csproj --diagnostics RS0016 --severity error
```

The command adds entries for new and changed members (RS0016). It doesn't remove entries for deleted members, so delete those lines from `PublicAPI.Unshipped.txt` by hand; the RS0017 errors name them.

Review the diff of `PublicAPI.Unshipped.txt` like code: it is the public API change. During 0.x, StellarAdmin makes no API stability promise, so everything stays in Unshipped and the Shipped files stay empty. When releases start promising a stable API, move the Unshipped entries to Shipped at each release. The packaged projects also report CS1591 for a public member without an XML comment.

## File encoding

Preserve each existing file’s encoding, UTF-8 BOM, and line endings when editing it. Do not strip or add a BOM as a side effect of reading and rewriting text; this can conflict with the encoding already selected in the user’s editor.

## Resource redesign baseline

`AddResource<TResource>()` automatically adds a sidebar link to the resource index through one shared admin panel provider. The link label follows `PluralLabel` by default. `resource.SidebarItem(item => ...)` can override its `Label`, `Group`, `Order`, and `Visible` values. Resources default to the Resources group, sort by `Order` within a group, and keep registration order for ties. `AddEfCoreResource<TContext, TEntity>()` uses the same registration path. Hidden links leave resource routes available. `AddSidebarLink(label, SidebarLinkTarget.Page/Action/Url(...))` adds links to host Razor Pages, MVC actions and URLs through a second provider. `SidebarViewComponent` passes every provider's items through the internal `SidebarItemsMerger`, which merges groups with the same label where the label first appears and stable-sorts links by `Order`; the sidebar and command palette render the merged list. Page and action targets store an empty area so link generation leaves the StellarAdmin area. The admin panel layout and the views it renders (the sidebar view component view, `_CommandPalette`, `_RemoteSheet` and `_SheetLoading`) reference each other by full path, so host pages can use the layout through the public `StellarAdminLayouts.Default` path; keep new layout partials on full paths. `sandbox/AdminPlayground` renders its `Pages/Reports.cshtml` page in the admin panel layout and links it in the Commerce group, `HomeController.Privacy`, and an external URL opened in a new tab. Sidebar link HTTP tests live in `tests/StellarAdmin.IntegrationTests/Sidebar`.

Resource routes use a slug: the kebab-case plural of the resource type name by default (`OrderItem` becomes `order-items`), or an explicit value passed to `AddResource<TResource>(slug)` or `AddEfCoreResource<TContext, TEntity>(slug)`. Slugs are lowercase letters and digits separated by single hyphens; a slug that isn't valid or that another resource uses turns the resource off, and a second slug for the same resource is ignored, each logged as a configuration problem (see the [configuration problems plan](plans/configuration-problems.md)). The slug is the MVC controller name, so application view overrides live in `Areas/StellarAdmin/Views/{slug}/`. `MapStellarAdmin` applies an internal outbound parameter transformer to the controller and action segments of the admin panel route only, so generated admin panel URLs are lowercase (`/stellaradmin/products/edit/7`) while action names, `asp-action` values and view names keep their PascalCase. Incoming requests still match case-insensitively; host application routes are unaffected. Verified 2026-09-28 with the admin panel unit (37), integration (195) and EF Core integration (59) test suites passing.

The old resource builders, page/default options, controller base, and query infrastructure have been removed. The admin panel retains its shell, page tag helpers, Razor views, editors, and rendering data definitions. The replacement `AddResource<TResource>()` registration configures typed labels, index columns, and an `IResourceDataSource<TResource>`. The shared resource controller renders index, create, and edit pages. Create forms now support explicit fields, nested sections/rows/groups, validation, and persistence. Edit supports explicit keys, record lookup, configured-field updates, and missing-record handling. Delete uses a shared index confirmation dialog and an antiforgery-protected POST through the data source. Data source write operations return ResourceOperationResult for success, not-found, or validation rejection. Rejected create/edit submissions preserve entered values and show field or summary errors. Rejected deletes redisplay the index with a validation summary. `IResourceDataSource<TResource>` provides listing through `ListAsync(ResourceListRequest, CancellationToken)`, returning `ResourceListResult<TResource>` with items and their total count before paging. Index paging is opt-in through `EnablePaging`. Sources apply stable ordering and paging, and null paging requests all matching resources. Sources opt into create, edit, and delete handler interfaces or implement the combined `IResourceCrudDataSource<TResource>`. `AllowCreate<TModel, THandler>()` pairs a separate create model with a handler, `AllowEdit<TModel, THandler>()` does the same for loading and updating a separate edit model. Ordinary create and edit continue using TResource. Unsupported actions are hidden and reject direct requests. Configured actions without implementations are turned off and logged as configuration problems. `sandbox/AdminPlayground` demonstrates Customer with separate custom create and edit models using its in-memory source. Product now uses a separate in-memory SQLite database through ProductDbContext, resets to 37 seeded products on startup, and exposes create, edit, and delete through the shared resource controller. Its two-decimal prices are stored as integer cents for SQLite sorting. Create, edit, and delete must be explicitly registered through their builder methods; a handler implementation alone does not enable an action. Repeated action registration replaces its previous configuration. The Customer password fields demonstrate validation only and do not create authentication accounts. Its Identity user and role resources demonstrate account management with manager-backed handlers. `RequireAuthorization` on the admin panel and resource builders adds endpoint authorization metadata through `MapStellarAdmin`. Requirements accumulate, and the asynchronous `ISidebarItemsProvider` lets the resource provider hide links the user cannot open. Authorization HTTP tests live under `tests/StellarAdmin.IntegrationTests/Authorization` and use the header-based `TestAuthenticationHandler`.

EF Core and its SQLite integration tests are in `StellarAdmin.slnx` and build/release verification. `AddEfCoreResource<TContext, TEntity>` supplies key discovery, listing, and opt-in CRUD through the shared controller. EF search and scope predicates filter before counting and paging through the shared search UI and scope tabs. Column sort expressions override database ordering while preserving the shared sorting UI. Initialized EF-owned objects can be configured through ordinary column and form selectors such as `product => product.Details.Sku`; the Product playground demonstrates rendering, sorting, creation, and editing of that property. `UseEditor<SelectEditor>` renders reference selects on create/edit forms, including custom models. The choice editors' EF Core `UseItems<TContext, TEntity, TValue>` extension requires value and text expressions; fixed lists, asynchronous loaders, and application `IChoiceItemsProvider` implementations are available through other `UseItems` overloads. The playground's Product–Category index column displays the CategoryId value directly. Query transformations and data-source event callbacks remain deferred for a broader API design. The separate Identity package and playground were removed; AdminPlayground demonstrates host-owned Identity users and roles through ordinary resources.

The old Dashboard unit tests, Dashboard integration tests, EF resource integration tests, and shared Dashboard.Testing host have been deleted. The active solution command runs the UI unit and HTTP integration tests, the admin panel unit and HTTP integration tests, and the EF Core SQLite HTTP integration tests. Admin panel resource work follows the [integration-first test strategy](conventions/unit-testing.md#admin-panel-test-strategy). Unit tests are limited to invalid configuration, DI registration contracts, and provider isolation. Integration scenarios live under `tests/StellarAdmin.IntegrationTests/Resources`, with shared host setup under `Infrastructure`, sample types under `Fixtures`, and real Razor overrides under `Areas/StellarAdmin/Views`. The HTTP tests cover real application Razor overrides, repeated builder configuration, index routes, label overrides, columns, encoded cell values, empty results, request-scoped data sources, and create/edit form rendering, validation, binding, persistence, key protection, missing records, deletion, and antiforgery protection using the shared Razor views. The remaining legacy rendering coverage has not been restored.

## Home page setup checklist

`HomeController.Index` calls `SetupStatusResolver.ResolveAsync` first. Outside Development, or when `ConfigureHomePage(home => home.ShowSetupChecklist = false)` turned the checklist off, it returns `null` before resolving any service or scanning, and the page links to the resources the sidebar shows the current user (or an empty state). Otherwise the resolver reads the options and the request: resource registrations, authentication schemes, authorization metadata on the home endpoint plus the fallback policy and global MVC `AuthorizeFilter`, branding, user menu changes from their defaults, the first app-relative added stylesheet, and sidebar groups, orders, icons and links. `EntityCandidateScanner` finds EF Core contexts by the type name of their `DbContextOptions<TContext>` registration, without an EF Core reference, and lists their `DbSet<T>` properties; it reads the service collection on first use and caches the result. The detection code is in `src/StellarAdmin/Home/`, and the step copy, code and agent prompts in `Home/SetupSteps.cs`. The views are `Areas/StellarAdmin/Views/Home/Index.cshtml` and its `_Setup*` and `_HomeResources` partials; the code block and copy button rules are in `Client/css/client.css`. The remembered tab and copy script is inline in `_SetupChecklist.cshtml` rather than in the panel JS, because it must run before the deferred components load to avoid a flash of the wrong tab. Unit tests are in `tests/StellarAdmin.Tests/Home`, and HTTP tests in `tests/StellarAdmin.IntegrationTests/Home` and `tests/StellarAdmin.EntityFrameworkCore.IntegrationTests/Home`. The prototype is `sandbox/html/home-setup.html`.

## Conditional local workarounds

These came from earlier sessions on Jerrie's machine; they are not universal build requirements. Recheck the environment before using them:

- If .NET downloads hang because of the local IPv6 route, prefix the command with `DOTNET_SYSTEM_NET_DISABLEIPV6=1`.
- If a build reports NETSDK1226 about missing prune package data, retry with `-p:AllowMissingPrunePackageData=true` and report the workaround.
- Earlier workspace sessions could accidentally bypass the product SDK pin. Run commands from the product root so `global.json` selects the intended SDK; do not change the pin to accommodate a machine.
- If the formatter tool shim fails despite restoring tools, inspect the installed tool and SDK. A cached `~/.nuget/packages/.../CSharpier.dll` path is machine/version-specific and should not be the shared default.

Do not change user-wide configuration as part of routine project setup. Report skipped checks and environment failures without claiming validation passed.
