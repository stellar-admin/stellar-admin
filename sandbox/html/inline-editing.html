Inline editing on index grids

Six ways to change a record without leaving the index page. Every grid works: edit, tab, press Enter or Escape. Saves are simulated with a short delay. Validation to try: an empty Name, a Price of 0 or less, or a non-whole Seats value. The concepts are not exclusive; a resource could combine, for example, 1 or 2 with 6.

Shared groundwork · needed once by 1, 2, 3 and 4, partly by 6
  • Settings for what can be edited. A column opts in to inline editing and maps to a field on the edit form. Edit can use a different model type from the index (ResourceEditOptions.ModelType, EditLoader) and columns can be nested paths (Details.Sku), so a column is only editable when its name matches an edit field; checked at startup with a clear error.
  • A save endpoint for some of the fields. Loads the record as EditPost does, binds only the submitted fields, validates and calls the existing EditHandler/UpdateAsync. Mostly restructuring: TryBindConfiguredFieldsAsync already binds a set of fields, so the data source doesn’t change.
  • Showing the saved row again through its display templates: either re-request the index with the current query and select just that row (cheap), or render a single grid row on its own, which the data grid tag helper doesn’t do today (real work).
  • Compact editors. The editor templates are built for the form (label, description, full size). Cells need a small, label-less version with errors on the cell. Text, numbers, select, switch and date are straightforward; lookups (LookupSheet, MultiLookupSheet) don’t fit in a cell and would be left out at first.
  • Permissions and token. Respect CanEdit, include the anti-forgery token, and keep working with the htmx swaps the index already does for search, scopes, paging and delete.

Suggested order: start with 5 or 6 (least cost, most reuse); 2 next, since it builds most of the groundwork 1 and 3 reuse; hold 4 until someone needs bulk editing.

1 — Click a cell to edit it

Spreadsheet-like. A cell becomes a field in place; each cell saves on its own.

  • Commit: Enter or clicking away saves; Esc cancels; Tab saves and opens the next editable cell. Errors keep the field open with a message under it.
  • Best for: quick corrections to one value. Weak at: discoverability, fields that depend on each other, touch.
Complexity 3.5 / 5 · Shared groundwork + the most browser-side work
  • Same server side as 2, but one request per cell.
  • Opening on click or double-click, with the editable-cell hint (outline, pencil or underline).
  • Saving on blur without racing clicks and htmx swaps; Tab moving across cells and rows while a save is still in flight.
  • Putting focus back after the cell swaps; showing errors without the layout jumping.
  • Fields that depend on each other can’t be validated properly one cell at a time.
  • Risk: fiddly to get right and to test.

2 — Row edit mode

The existing Edit action turns the whole row into fields; the action buttons become Save and Cancel. One row at a time, the rest dim.

  • Commit: Save or Enter; Cancel or Esc. The row saves as one request, so cross-field validation works.
  • Best for: records whose list columns are most of what matters. Weak at: wide grids (fields squeeze), columns not shown in the grid.
Complexity 3 / 5 · Shared groundwork
  • Render a row in edit mode: compact editors in editable columns, plain text in the rest, Save and Cancel in place of the actions.
  • One request per row, so cross-field validation works as on the edit page.
  • Re-rendering a single row after save (see the shared groundwork).
  • Freezing column widths while editing (the prototype does this); one row at a time; Enter and Esc.
  • Bonus: builds most of the shared groundwork that 1 and 3 would reuse.

3 — Popover editor

Clicking a value opens a small form anchored to the cell: label, field, help or error text, Cancel and Save. The grid itself never changes shape.

  • Commit: Save or Enter; Esc or clicking outside cancels.
  • Best for: fields that need room (long text, lookups, a date picker) or explanation. Reuses the field editor templates as-is. Weak at: many edits in a row (one popover per value).
Complexity 3 / 5 · Shared groundwork
  • An endpoint that renders one field’s editor in a popover; the editor can be close to the full-size form editor (label, description, error), so less compact-editor work than 1 and 2.
  • The library’s popover anchoring already exists.
  • Focus returns to the cell when the popover closes.
  • Open question: lookups would open a sheet from inside a popover (stacking and focus).

4 — Grid edit mode (batch)

An “Edit grid” toggle turns every editable cell on the page into a field. Changed cells are marked; a save bar counts the changes and saves them all at once (or discards them).

  • Commit: Save all. Enter moves down a column, Tab across. Leaving with unsaved changes would warn.
  • Best for: bulk updates (prices, stock, statuses). Weak at: paging and sorting mid-edit; partial failures need per-cell errors.
Complexity 4.5 / 5 · Shared groundwork + a new batch save
  • Everything from 2, for every row at once.
  • Tracking which cells changed; the save bar.
  • Binding many rows in one post (form names prefixed per row).
  • A batch save, and a decision on partial failure (all-or-nothing vs per-row); errors mapped back to the right cells.
  • An unsaved-changes guard that also covers paging, sorting, search and scopes, which all swap the grid through htmx.
  • API impact: probably a new batch-update method or handler on the data source.

5 — Form in the row details

Edit opens a form under the row, in the row details band, with every editable field (including ones not shown as columns, such as Description). It is the edit page's form, loaded on demand.

  • Commit: Save or Cancel buttons, like the edit page. The row updates in place after saving.
  • Best for: full edits without losing your place in the list; reuses the form page's layout and validation. Weak at: very quick single-value changes.
Complexity 2.5 / 5 · Barely; reuses the edit form
  • Reuses the most: row details already load on demand (RowDetail, hx-get), and _FormFields already renders the edit form with its sections, groups, lookups and validation.
  • New: an endpoint that returns the edit form inside the row details, and a save that either returns the form with errors or closes the details and updates the row.
  • Decide how it coexists with resources that already have row detail panels.
  • Mostly server and Razor work, little new JavaScript.
  • Risk: wide multi-column form layouts inside the table.

6 — Direct controls only

Only the values that are a single choice are editable, and their control is always there: a switch for Featured, a badge that opens a status picker. Changes save immediately with an Undo.

  • Best for: publish/feature/active toggles and workflow states. Smallest API and the lowest risk. Weak at: anything typed.
Complexity 2 / 5 · A small part of the groundwork
  • Limited to booleans and enums or selects.
  • A switch or badge picker in the cell that posts on change through the partial-save endpoint.
  • Undo through the toast, re-posting the previous value.
  • No editing mode, keyboard handling or layout changes: least work, least risk.
  • New: the badge-shaped picker, as a small component or a Select variant.
