Prototype · Multiselect · Tom Select 2.6.2

Tom Select, dressed as a StellarAdmin control

Every field below is a plain server-rendered <select> (most of them multiple) enhanced by Tom Select. Tom Select's stylesheet is not loaded: the control, chips, dropdown and options carry the sa-combobox-* classes the generated shadcn themes already ship, plus a small structural block (the <style> in the head) that would become .sa-* rules. Swap themes and dark mode from the bar at the bottom right — the hand-authored themes fall back to the token-only rules. Each field shows what the form would post.

Integration notes

Wrapping

The editor template keeps rendering a real <select multiple name="…"> with the selected options (value + title, media and description as data-*), so model binding, validation attributes and no-JS posting stay exactly as they are. A small Lit element (for example <dashboard-multi-lookup>, or a library-level sel-combobox) wraps it, calls new TomSelect(select, settings) in connectedCallback and destroy() in disconnectedCallback — so htmx swaps and the create sheet re-initialise cleanly. Settings come from data-* attributes the tag helper writes (min length, max items, create, URL).

Remote search points load at the existing lookup results endpoint. That endpoint renders HTML today (_LookupResults: sa-command-items with a <template data-lookup="selection">); the clean option is a JSON variant of the same query (value, title, description, media) feeding Tom Select's string templates. Paging maps onto the virtual_scroll plugin (firstUrl / setNextUrl), which is "load the next page on scroll" rather than DOM virtualisation. Server results should not be re-scored client-side: pass score: () => () => 1, as demo 2 does.

Styling

  • Skip tom-select.css entirely. Use the class options (controlClass, itemClass, dropdownClass, dropdownContentClass, optionClass) plus the plugins' html options to emit our classes and data-slots.
  • The active option needs a data-highlighted and selected options a data-checked — Tom Select only toggles .active / .selected. The 30-line sa_theme plugin on this page does that sync; it would ship in the wrapper.
  • The shadcn themes already contain .sa-combobox-chips / -chip / -chip-remove / -content / -list / -item / -label (generated, never used). The hand-authored themes need those rules added; until then the token-only fallback here is what they render.
  • Structural rules (wrapping control, hidden select, dropdown positioning, single-mode value) go in components.css; the theme-coverage manifest needs the new hooks.

Size and licence

  • tom-select.complete.min.js (every plugin): 51.8 kB minified, 17.5 kB gzipped.
  • tom-select.base.min.js (no plugins): 41.8 kB minified, 14.8 kB gzipped. Importing tom-select/base plus the 3–4 plugins we use into stellar-admin.js through rolldown lands around 16 kB gzipped. Dependencies: @orchidjs/sifter and @orchidjs/unicode-variants (bundled).
  • The unused stylesheet would have been another 2 kB gzipped.
  • Apache-2.0 — compatible with our MIT package, but it needs its NOTICE/licence text carried in the bundle's third-party notices.

Accessibility

  • The search input is role="combobox" with aria-expanded, aria-controls and aria-activedescendant; the dropdown is a role="listbox" of role="option"s with aria-selected. Our label's for is moved to the generated input automatically.
  • Chips are not exposed as a list and the remove buttons are tabindex="-1": keyboard removal is ←/→ to walk chips and Backspace/Delete. Works, but undiscoverable for screen-reader users — worth a live-region "removed X" announcement.
  • With dropdown_input the focusable control is a generic div; needs a screen-reader pass before choosing that variant.

Gaps

  • The dropdown is position: absolute inside the wrapper: no top layer, no CSS anchor positioning, no flipping above the field near the viewport bottom. Inside a sheet or dialog with overflow: auto it gets clipped; dropdownParent: 'body' moves it out but then it is positioned once by JS on open and does not follow scrolling. A wrapper could instead move the dropdown into a [popover] with anchored-bottom-span-right try-flip-all — doable, but we'd be fighting the library.
  • No DOM virtualisation; thousands of local options are slow. Remote search avoids the problem.
  • drag_drop (reordering chips) requires jQuery UI — not an option.
  • No mobile/full-screen mode; on phones the dropdown is a small absolutely-positioned box.
  • Templates are HTML strings with an escape helper — our media/description markup gets duplicated from the Razor partials into JS (or rendered server-side into data-*).
  • Maintenance: steady releases (2.6.2, July 2026), ~420k weekly downloads, small core team.
